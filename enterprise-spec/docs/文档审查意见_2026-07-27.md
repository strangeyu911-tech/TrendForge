## 一、必须修的硬伤（Broken —— 照搬会出错）

### 1. SQL §3.4 A/B 显著性检验 SQL 引用了未定义的列
`SQL数据看板设计.md` 第 255-276 行：
```sql
CASE WHEN abs(avg_ctr_diff) / sqrt(avg_ctr_var/n) > 1.96 THEN 'significant' ...
```
- `avg_ctr_diff`、`avg_ctr_var`、`n` 在 `SELECT`/`GROUP BY` 中均未计算，这段 SQL **无法执行**。
- 修正建议：显著性检验不要在 SQL 里硬算。改为先按 variant 聚合出 `avg_ctr`、样本数 `n`、方差，再用 `python`（scipy）做两比例 Z 检验；或补全程式化子查询（用窗口函数算组内方差）。当前 A_B实验方案.md 已规定用 Z-test / scipy，SQL 里只需输出每 variant 的 `avg_ctr` 与 `n` 即可。

### 2. SQL §3.1.3 在 WHERE 中使用聚合函数（非法 SQL）
`SQL数据看板设计.md` 第 156-168 行：
```sql
WHERE dt >= CURRENT_DATE - INTERVAL '7 days'
  AND SUM(impressions) >= 1000   -- ❌ 聚合不能放 WHERE
```
- 应为 `HAVING SUM(impressions) >= 1000`（GROUP BY content_id 之后）。

### 3. Prompt §7.1 引用了不存在的数据表
`Prompt版本管理方案.md` 第 246-256 行：
```sql
FROM content_metrics
WHERE published_at >= NOW() - INTERVAL '7 days'
```
- 但 `SQL数据看板设计.md` 定义的表是 `dwd_content_fact` + `dws_content_daily`，**没有 `content_metrics` 表**。
- 修正：改为 `FROM dwd_content_fact f JOIN dws_content_daily d USING(content_id)`，字段 `ctr`/`read_rate` 取自 `d`，`bad_case`/`prompt_version` 取自 `f`（与 §3.3.1 写法保持一致）。

## 三、高风险设计缺口（影响可行性 / 合规性）

### 1. 合规 / 政治红线引擎设计缺失 ⚠️
- PRD §10 将「合规风险」列为 **高** 等级，缓解措施依赖「敏感词库 + 政治红线规则 + 人工介入」。
- 但 **没有任何一篇文档** 定义：敏感词库由谁维护、如何更新、版本如何管理；「政治红线模型」（Agent §7.4）是什么模型、训练/评测方式、误杀率如何控制。
- 风险：高风险的合规能力是「幽灵需求」。建议新增 `合规与内容安全设计.md`，或至少在 Agent 架构中补一节「合规引擎 I/O 契约 + 词库治理 + 人工兜底 SLA」。

### 2. Bad Case 库缺 DDL
- Bad_Case §4 定义了 Bad Case JSON 记录，Workflow §6.2 说 `reason 入 Bad Case 库`，但 **全仓无 `bad_cases` 表结构**。
- 建议补 CREATE TABLE（bad_case_id / content_id / category_l1/l2 / severity / root_cause / affected_prompt_versions / status / assigned_to / sla 等），与 `dwd_content_fact.is_bad_case` 关联。

### 3. 安全 / 鉴权 / 密钥管理设计缺失
- PRD §6 列「API 鉴权 / 敏感信息脱敏 / 全链路鉴权」，RAG §11 只讲数据合规。
- 缺：LLM 供应商 Key 管理、内部服务 mTLS / Token、Kafka 鉴权、Prompt 库访问权限（含双人审批的实操落点）。建议补安全小节或独立 `安全设计.md`。

### 4. 灰度发布（canary）与 A/B 实验分桶关系未澄清 ⚠️
- Publisher PB-2 做「10% 灰度观察 CTR」；A_B实验 §3.3 按 `content_id` 哈希分桶做 50/50。
- 两者机制重叠但文档未说明：Publisher 灰度是否复用 A_B 分桶框架？若两条独立分桶链路并存，存在 **双重分桶 / 实验污染** 风险。
- 建议：明确「Publisher 灰度 = canary（无对照，仅观察护栏）」，与「A/B 实验 = 有对照分组」区分，并说明二者如何共存（例如 canary 不走 experiment_assignments）。

### 5. 多语言 / 翻译质量风险未进风险登记
- PRD §4.2 多语言为 P1（中/英/日/韩），但 §10 风险表无「翻译准确性 / 跨语言事实一致性」条目。
- 日/韩生成与互译是事实错误高发区，建议补一条「多语言质量风险（中）」并给缓解（翻译保留原文链接 + 跨语言 Reviewer 校验）。

### 6. 成本模型未与 ¥0.5 目标对账
- Workflow §10 说峰值 500 任务/分、20 Worker；RAG §9 列了向量/GPU 节省。但无一份把「LLM 调用 + 向量推理 + 存储 + 带宽」汇总成单条成本的测算，也未验证能否压到 ¥0.5。
- 建议补一张成本测算表（按 P50 链路 Token 数 × 单价），作为 KR4 的可行性背书。

## 四、范围 / 表述歧义（建议澄清）

1. **封面图 scope 矛盾**：PRD §1.3 Non-goals 写「本期不覆盖图像/视频生成（仅文本 + 封面图）」——「仅文本+封面图」似暗示封面图本期做；但 §4.2 多模态行写「封面图生成（下一期）P2」。建议 Non-goals 改为「本期不生成封面图，Writer 仅输出封面建议文本」，消除歧义。
2. **北极星口径**：PRD §8.1「总阅读时长 / 总曝光量」维度上 = 每次曝光平均阅读时长；看板 §4.2 又称「人均阅读深度」。建议统一为「篇均阅读时长」或「人均阅读时长」，并明确分母（曝光 / 人）。
3. **悬空引用**：PRD §7/§11 及多文档引用 `dashboard/index.html`、`architecture/index.html`、`demo/`，但这些产物不在 `docs/`，也未在仓库中。建议：要么补产出、要么在文档中标注「待建设」状态，避免评审误以为已存在。
4. **多语言模板示例不全**：Prompt §4.2 多语言变体只列 zh/en/ja，缺 ko（PRD 要求中英日韩）。属示例遗漏，补一行即可。

## 五、建议补强的细节（非阻塞）

- **Reviewer 严格度**：§7.4 规定「事实不一致 ≥1 即 revise」。对单条孤立错误即整篇回退可能偏严，建议加「严重度阈值」（critical 不一致才回退，minor 标注放行），并与此对应 Reviewer strict 配置（Workflow §9.1 已有 politics 严格开关，可扩展到 fact）。
- **数据回流闭环自动化程度**：Prompt §7.3 说「触发优化任务 → 编辑评审后起新版」，本质是半自动。PRD 痛点强调「闭环」，建议明确自动化边界（哪些自动、哪些需人审）。
- **实验样本量口径**：A_B §3.2 以曝光计（n≈39,000/组），但实验报告示例以「篇数」（412/408 篇）呈现，未给曝光数。建议报告模板补「总曝光 / 组」一列，避免误读。
- **撤回演练/Runbook**：PB-4 撤回 5min 是强承诺，建议补一份「全网撤回 Runbook + 演练频率」，否则只是数字。
